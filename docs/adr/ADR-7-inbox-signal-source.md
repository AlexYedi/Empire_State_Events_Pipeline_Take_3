## Context

The inbox is a high-value, under-utilized source. Today one thin pipe connects it: `label:Content/newsletters` → Notion Topics (`trend-radar` / `/morning-refresh`). Direct-from-company product-update / development / funding / exec-move signals, event invites, and job/recruiter mail all arrive and decay unstructured; high-frequency promotional senders bury the signal. The MI graph already models a signal as an `event` row (`kind` + `source` + `confidence` + provenance) linked to entities via `event_entity` — so an email-mined company/product signal needs **zero new tables and no new `kind`** (`launch` / `market` / `funding` / `exec_move` already cover it). What is genuinely new and warrants a record: (1) treating email as a first-class, routinely-produced signal **source**; (2) **expanding the Gmail connector from read-only to label-write** so the channel can be brought to order in-place; (3) pointing the scan at the **whole inbox minus a denylist**, which touches private mail (the SEC/PII intersection, YED-81).

## Decisions

1. **New producer `inbox_miner`, writing existing `public` tables only.** Signals become `event` rows (`kind` ∈ `launch`/`market`/`funding`/`exec_move`), `source` prefix `inbox_miner:<class>`, mandatory `url` + `metadata.sources` provenance, `confidence` 0–1, `relevance_score` left 0 (owned by the recompute producer). Referenced companies/topics upsert on `lower(name)` (`Prefer: resolution=merge-duplicates`); people are read-before-write and **never fuzzy-merged** (ADR-4 / migration-playbook). Linked via `event_entity` hyperedges. **No DDL, no new `kind`, no intelligence-schema writes.** REST with `SUPABASE_API_KEY`, never the Supabase MCP. The graph write is **additive, never a gate** — a Notion write and/or the digest stand on their own; a REST failure is logged and the run continues.

2. **Gmail connector expands to label-write, plus a batch-gated mark-spam for noise reduction (scope expansion — the genuinely irreversible-ish authorizations here).**
   - **Labeling (routine, per-run):** the miner may `create_label` and apply labels (`Pipeline/company-signal`, `Pipeline/event`, `Pipeline/job`, `Pipeline/offer`, `Pipeline/processed`, `Pipeline/unsubscribe-candidate`, `Pipeline/signal-source`). `Pipeline/processed` is the **idempotency key**.
   - **Noise reduction (the goal is signal↑ AND noise↓, per Alex 2026-09-09):** Stage-A discovery surfaces a **suspected-spam sender list** for review. On Alex's **explicit en-masse approval only**, the miner then, for those senders: (a) adds them to `inbox-denylist.md`, and (b) applies `mark_thread_spam` in Gmail (trains the filter to keep them out — the "block" action). Senders needing a real unsubscribe click or a Gmail filter rule (no MCP tool for those) go to an **unsubscribe worksheet** Alex actions manually.
   - **Hard limits:** the miner **never** trashes, deletes, sends, marks-read, or unsubscribes silently, and **never marks spam without a batch approval**. `mark_thread_spam` is reversible (spam→inbox), which is why it is allowed under a gate; trash/delete are not used at all.
   - **✅ SCOPE GRANTED + VALIDATED 2026-09-10.** The initial probe found the connector READ-ONLY (`create_label` → insufficient scope); Alex reauthorized with `gmail.modify`+`gmail.labels` and a fresh session confirmed it. **In-Gmail labeling is LIVE**: the `Pipeline/*` taxonomy exists (processed · company-signal · event · job · review · signal-source · unsubscribe-candidate) and 7 cohort threads were labeled + read back successfully. `Pipeline/processed` is now the PRIMARY idempotency mechanism (belt-and-suspenders with the canonical-URL event dedup and the `.claude/artifacts/inbox-miner-processed.jsonl` ledger). The **mark-spam noise-reduction batch is now technically unblocked** but still requires Alex's explicit en-masse approval per this decision — never silent.

3. **Scan boundary = a one-time METADATA-ONLY whole-inbox discovery pass to BOOTSTRAP an allowlist, then ALLOWLIST-ONLY body-reading, widened only via labels (revised 2026-09-08 after the `cto-principal-architect` pre-mortem + Alex's discovery-pass refinement; supersedes the initial recurring-whole-inbox-minus-denylist choice).** Two distinct read stages, kept apart because that is where the risk actually lives:
   - **Stage A — one-time discovery (metadata only, NO bodies).** A single bounded pass over the whole inbox reads **sender address + domain + subject + frequency + labels only** (`search_threads` / snippet — never `get_thread` bodies), denylist-pre-filtered (health/finance/legal/etc. categories excluded even here). It emits two Alex-reviewed worksheets from the same scan: (i) **candidate allowlist** — the high-signal company/product-update senders discovered (better coverage than hand-curation), and (ii) the **sender-frequency → unsubscribe** hygiene table. Subject-line metadata can still carry a little PII, so it is written only to these review worksheets, never to logs or the graph. Nothing is classified-for-routing or written in Stage A.
   - **Stage B — ongoing (bodies, allowlist-only).** After Alex curates the discovered allowlist (`.claude/references/inbox-allowlist.md`), all recurring runs read **bodies + extract signals only from allowlisted senders**. This is the expensive/risky stage (body ingestion, extraction, writes) and it is bounded to the allowlist **by construction**. New sources enter the allowlist **only via a hand-applied Gmail label** (controlled widening) — no recurring whole-inbox body-reading, ever.

   The denylist (`inbox-denylist.md`) remains a secondary safety net inside both stages. **Newsletters ARE in scope for the miner (corrected 2026-09-10).** The miner and `trend-radar` divide by **extraction lens, not source**: `trend-radar` pulls the *topic* dimension of a newsletter (what's rising), the miner pulls the *entity* dimension (which companies launched/raised/moved). The same newsletter feeds both with no architectural redundancy; the graph's dedup (topic/company upsert on `lower(name)`, event dedup on identity) absorbs any collision. Newsletters (`label:Content/Newsletters`, ~1,039 threads) are the densest company/funding/launch source in the inbox and are the **anchor of the allowlist**. (The only "double-process" concern is reading one body twice across two producer runs — a future shared-ingestion optimization, NOT a reason to partition sources.) Person PII (`person.email`) is written to the graph only where the schema already carries it and kept **off any anon-exposed `signal_read` view** (ADR-1/2); **no email bodies or PII in logs or the run-log** — only entity names, canonical topics, provenance URLs, and counts. Allowlist + denylist are Alex-approved before Stage B's first real run (Phase 0/1 gate).

4. **Trigger: PERMANENT write gate for v1 → morning cron only once dedup precision is MEASURED.** The approve-before-write gate is not a few-day shakedown — it is the **v1 write path** (Tier-2 digest-then-approve), and it renders the *resolved* write targets (matched-existing-row-id vs will-CREATE; the exact dedup identity; the provenance payload as it will be stored; a one-line why-genuine-signal) so fragmentation / false-merge / misattribution / PII-in-provenance are caught by eye. Cron is the destination Alex chose and remains so — but it is **gated on a measured low false-merge rate** on real runs, not a fixed number of days. When earned: local-`launchd` morning cron running `claude` headless (on-subscription; `.env` loaded explicitly — cron does not inherit the shell profile; the command **hard-fails loudly if `SUPABASE_API_KEY`/Notion creds are absent**, never proceeding to labeling), append-only, every write reported in the morning digest (matching `/morning-refresh`). Cloud routines only if billing-to-subscription is confirmed.

5. **Extraction & write-safety invariants (from the pre-mortem — correctness, not preference).**
   - **No `person` rows are created from inbox senders in v1** — company/product signals need `company` + `event` + `event_entity` only. Keeps contacts' PII out of the graph.
   - **Provenance shape is fixed:** sender **domain** + RFC **message-id** + received **date** + the **canonical primary URL**. The URL MUST be **redirect-resolved** to its true destination (newsletter/mailer links are tracking redirects) and stripped of tracking params — a redirect or the newsletter-issue URL is NOT a valid source (fails rule #12). Redirect-resolution doubles as a veracity check: if the resolved primary source contradicts the newsletter's claim, flag `verify_before_content`. Never raw body text, never a personal email address. (Proven 2026-09-10: resolving a GTM-Engineer-Pulse item surfaced an investor discrepancy — newsletter said Founders Fund, canonical source said Benchmark.)
   - **Company key is a deterministic slug**, not raw `lower(name)`: strip legal suffixes (Inc./LLC/Corp.), punctuation, collapse whitespace, canonical casing; maintain an alias map. Resolve-against-existing-and-show-the-target at the gate rather than blind-upsert (prevents both fragmentation and false-merge).
   - **Dedup identity — AMENDED 2026-09-10 (cohort-eval findings I1/I2): the key is the CANONICAL (redirect-resolved) URL**, not `(company-id, kind, date-bucket)`. The original `(company-id, kind, date-bucket)` identity recorded here was falsified by the v1 cohort: OpenAI shipped Navier-Stokes AND Images-2.5 on the same day (same company, same kind, same date) so that tuple **wrongly merges two distinct events**, while the *same* story cited by 4 different newsletters must merge to one row — the canonical URL does both correctly. `(company-id, kind, date-bucket)` survives only as a coarse fallback when a signal genuinely has no URL. The LLM-generated `event.title` is a display field, never a key. Shipped in `inbox-miner` SKILL B3 Step 2 + `.claude/scripts/inbox_signal_write.py` (`dedup_event()`), validated idempotent 2026-09-10.
   - **Writes come only from a schema-validated structured extraction, never from free email text** — the distill/classify subagent returns text/structured data only and is never given write tools (SDK rule enforced here for security: email is attacker-controlled input and the writer key bypasses RLS). The miner has **no delete/DDL path** at all.
   - **A pre-extraction signal filter runs before routing:** "is this a genuine market/launch/funding/exec-move signal, or marketing / transactional / cold-outbound / personal?" Non-signal mail is filtered out *before* extraction; low-confidence → **abstain** (label for review, write nothing).
   - **No automatic full-history backfill** (bounded manual batches only); a **standing weekly dupe/orphan-edge sweep** query guards the write-mostly graph; any signal whose company entity was **created this run** is flagged for human eyes before it may surface in content (rule #12 source-check).

## Options rejected

- **A new `email_signal` event `kind`** — rejected: `launch`/`market`/`funding`/`exec_move` already model company/product signals; a new kind fragments the taxonomy and would need consumer changes for no gain. Email origin is carried in `source`/`metadata`, not `kind`.
- **A new `email`/`message` table (per-message persistence)** — rejected for v1: violates the "no DDL, additive-only, conform-to-the-contract" discipline; the signal is the durable object, the email is provenance (`url` + `metadata`). Revisit only if "which email produced this" becomes a first-class need.
- **Keep Gmail read-only, order lives only downstream** — rejected by Alex: "bring order to the channel" is an explicit goal; in-Gmail labels are the reversible, visible way to do it and give a free idempotency key. (Auto-*unsubscribe*/delete stayed rejected — outward-facing / destructive, manual only.)
- **Recurring, body-level whole-inbox scan (the initial choice, reversed 2026-09-08)** — rejected after the pre-mortem: reading all non-denylisted *bodies* on every run to classify them puts personal-mail content into transcripts/telemetry (ADR "no PII in logs" pressure), leans on the denylist being exhaustive (fragile), and compounds daily under cron (R1/R2/R9). **Note what is NOT rejected:** a *one-time, metadata-only* whole-inbox pass (sender/domain/subject/frequency, no bodies) to bootstrap the allowlist + unsubscribe table (Decision 3, Stage A). The rejected thing is *recurring body ingestion* over the whole inbox; ongoing body-reading is allowlist-only. *(Promotions/Updates-only was an offered middle; the discovery-pass-then-allowlist design was chosen.)*
- **Cron on day 1** — rejected: an unattended writer on an unproven classifier with an RLS-bypass key, reading private mail, is the worst-outcome path (R3/R4/R6/R10). Cron is deferred behind the permanent write gate + a measured false-merge rate (Decision 4).
- **Route all four streams in v1** — rejected: events/jobs/offers have weaker dedup (no GCal/ATS id) and offers have no schema home; routing them half-built pollutes. v1 classifies + auto-labels them (lossless capture) and routes only the clean company-signal stream. *(The read-only sender-frequency / unsubscribe table carries zero graph-write risk and ships early regardless.)*
- **Supabase MCP for writes** — rejected as always (different account; REST-only per ADR-0).

## Consequences

- **Positive:** the inbox becomes a routine MI producer (the first company-*anchored* one); zero schema change; the channel gains in-place order + a free idempotency key; lossless capture of events/jobs/offers for later phases; reversible by construction (Notion/graph writes are additive, labels are removable, cron is one file).
- **Costs / standing watches:** a broad scan of private mail (denylist + PII-off-logs are the controls, and they are only as good as the denylist Alex curates); classifier precision on company-name extraction directly gates graph cleanliness (see risk table); the Gmail label-write scope is a live dependency to verify; unattended cron writes require the shakedown to have earned trust first.
- **Risk table (v1) — from the `alex:cto-principal-architect` pre-mortem (2026-09-08), ranked; R1–R5 are the do-not-ship-without-fixing tier:**

  | # | Risk | L | I | Mitigation (where handled) |
  |---|---|---|---|---|
  | R1 | Personal-mail PII enters via the **read/classify** stage (transcripts/telemetry) even though only company signals route | H→L | H | **Allowlist-first scope** (Decision 3) bounds reads by construction; strip body/snippet from anything reaching a log or the telemetry emitter. |
  | R2 | Contacts' emails materialize as `person.email` rows in the graph | H→L | H | **No `person` rows from inbox senders in v1** (Decision 5); provenance = domain + message-id + date, never a personal address. |
  | R3 | Idempotency depends on an **unverified** label-write scope → silent daily re-writes | H | H | Verify label-write live in Phase 1 before any cron; ledger fallback; label only *after* the DB write confirms. |
  | R4 | Worktree/cron has no `.env` → Supabase write silently no-ops while labeling still marks "processed" → signal lost forever | H→L | H | `.env` symlinked (done); command **hard-fails loudly** if keys absent (Decision 4); assert-writes-succeeded before labeling. |
  | R5 | `lower(name)` under-normalizes → company table both fragments ("OpenAI"/"OpenAI, Inc.") and false-merges (generic "the platform") | H→M | H | **Deterministic slug + alias map + resolve-and-show-target at the gate** (Decision 5). |
  | R6 | Prompt injection + RLS-bypass key in an unattended loop | M | H | Distill/classify subagent gets **no write tools**; writes from schema-validated extraction only; no delete/DDL path (Decision 5). |
  | R7 | LLM-invented `event.title` used as dedup key → over/under-merge | H→M | M | Dedup identity = `(company-id, kind, date-bucket)`; title is display-only (Decision 5). |
  | R8 | Misattributed hyperedge → wrong company gets a "development" → flows to a public LinkedIn claim (collides with rule #12) | M | H | Mandatory primary-source URL in provenance; created-this-run entities flagged for human review before surfacing (Decision 5). |
  | R9 | Whole-inbox classify-everything, daily, + full-history backfill = the rule-3 oversized-context / compounding-spend anti-pattern | M→L | M | Allowlist scope collapses volume; per-run cap; no auto full-history backfill (Decisions 3, 5). |
  | R10 | Write-mostly graph + first-of-its-kind producer → errors accrue invisibly for weeks | H→M | M | Permanent write gate for v1 + standing weekly dupe/orphan sweep (Decisions 4, 5). |

  *(The "→" shows residual likelihood after the adopted mitigation. The highest-leverage single control — the pre-mortem's §4 — is the permanent, resolved-target write gate, which catches R2/R5/R7/R8 in one surface and makes R3/R4 loud instead of silent.)*
