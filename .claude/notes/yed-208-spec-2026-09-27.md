# YED-208 spec: the `published` producer + the `content` lens (2026-09-27)

**Kind:** infra-classified (Alex, 2026-09-27): the architecture note (§3.2 lens presets, B5 `publish`, W3) already
specs it, and back-linking prior posts is an existing standing rule. This in-repo spec satisfies DoD item 1.
**Linear:** YED-208 (the `published` producer is scoped in, not split). **Builds on:** YED-205 (merged #134).

## Problem
Drafts never know what Alex has already published. The standing rule, "link new recaps back to your own earlier posts
on the same theme", lives in memory, so it happens only when someone remembers. The graph can't help: it holds zero
`published` events and zero `linkedin_post` documents. Notion holds 46 published posts, 41 with a URL, and every one
has an Event relation, but only 24 carry Topics.

## Decisions (Alex, 2026-09-27), each scoped
1. **Scope includes the `published` producer.** `substrate.py publish` turns each published Content Draft into
   `event(kind='published', url=<Published URL>)`, a `documents(source_type='linkedin_post', visibility='public_ok')`
   row, and an `artifact_outcome` row (Goal/Target now, Outcome when tagged). Posts **without** a Published URL are
   skipped and counted, because a back-link needs a URL.
2. **The post text is embedded,** one `doc_chunks` row per published **variant section** (`## Variant …` / `## Post …`),
   at most 3, each capped. **The internal preamble, visual brief and steering notes are never embedded**: the draft
   page mixes public post text with private working notes (one names a confidential round that was excluded). The
   text goes through the same `redact_body` confidentiality filter claims use. Notion does not record which variant
   shipped, so every variant is embedded; they share a theme, which is what the lens matches on.
3. **Edges:** the `published` event links the draft's own Topics (`tagged_topic`) and People (`subject`), **plus the
   topics of the event it covered** (read from the graph by that event's Notion page id). That covers the 22 posts
   with no Topics tag.
4. **New posts flow in through `/tag-outcome`** (Step 4.5 publish-sync), which already visits every published post.
   `publish` is idempotent: a post already in the graph with no new body only refreshes its `artifact_outcome`.
5. **The `content` lens** in `retrieve.py`: the claim weights from the architecture table, **except `w_use = 0`**
   (ADR-10 D8 outranks the table's 0.20 until ≥20 outcome rows exist). It adds a **"What you've already said"**
   section listing prior posts, found relationally (a `published` event sharing a seed entity) and by meaning
   (`match_doc_chunks` on the seed text, limited to `linkedin_post` documents). Each entry carries date, title, URL,
   outcome if graded, and why it matched. **URLs come only from the graph; a draft may never invent one.**
6. **Consumers:** `pre-event-content` (new Step 1.8) and `content-correspondent` pull the pack before drafting and
   back-link prior posts **only where one genuinely extends the new post's thesis**. The acceptance test demands ≥2
   in a real run; the skill text does not force a quota.

## Failure modes considered
A PII-bearing post body (one post refused and counted, never a crashed run) · a draft with no variant headings (fall
back to the redacted body, minus the preamble) · an edited post (the document versions by hash, and the new version
gets its own chunks) · an empty prior-post set (the section says "none yet", never an error) · the RPC during a
future freeze (`match_doc_chunks` is STABLE, i.e. read-only, so it joins `READ_ONLY_RPCS`).

## Acceptance
- [ ] Backfill: the 41 URL-bearing posts are in the graph; a re-run reports `created=0`
- [ ] `retrieve.py --lens content` on a real upcoming event lists ≥2 prior posts with URLs
- [ ] A real `pre-event-content` run back-links ≥2 prior posts from the pack (architecture plan W3 proof)
- [ ] Selftests green; spine_client selftest + check-writers clean; judge ran in session; DoD closed

## Pre-mortem (before the judge, 2026-09-27)
*A month from now, the back-links in a draft are wrong or useless. What happened?*
| # | Imagined failure | Verdict | Change |
|---|---|---|---|
| 1 | **Roundups crowd the list.** A weekly roundup inherits the topics of 3–8 covered events, so it matches almost any seed and pushes out the focused posts worth linking. | **Real.** | Relational hits rank by **number of shared seed entities**, then similarity, then recency. Pinned in `retrieve.py --selftest`. |
| 2 | **Private working notes leak into the graph.** Draft pages carry an internal preamble, and one names a confidential round that was excluded. | **Real risk.** | Only variant sections are embedded; the preamble, visual brief and first comment never are; `redact_body` still runs. A page with no headings yields nothing. |
| 3 | **One PII hit crashes the whole backfill, or leaves a half-written post.** | **Real, found by a selftest.** | The ADR-9 guard runs on the post text **before any write**; a refused post writes nothing and the rest continue. |
| 4 | **Wrong dates rank old posts as fresh.** Notion has no publish date. | **Real.** | `Posted YYYY-MM-DD` from the LinkedIn-export outcome note, else the earliest covered event's date; never the grading date. |
| 5 | **The hub starts listing posts as events.** | **Checked: no.** The hub reads `kind=eq.market` only. | None. |
| 6 | **A draft invents a URL.** | **Guarded in the skill text.** | Pack URLs only, verbatim; if the pack has none, there are none. |
| 7 | **A network stall aborts the backfill.** | **Real today:** many requests stalled about 8 s, some failed. | Read-only transport retries in `spine_client.req` (writes never retried); every verb is idempotent, so a re-run resumes. |
| 8 | **Which variant shipped is unknown.** | **Accepted.** Notion does not record it. | All variants are embedded; they share a theme, which is what matching needs. |
