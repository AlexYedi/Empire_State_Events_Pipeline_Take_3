# The inbox scan boundary as a mechanism (denylist v1 → enforced in code)

> **Linear:** YED-161 · **Date:** 2026-09-13 · **Owner:** Alex · **Status:** SHIPPED (#74 mechanism, #75 denylist v1 accepted) · **Appetite:** <3d · **Backfilled?** no · **Depends on:** YED-81 (ADR-9, shipped #73)

**1. Problem & why now.** `inbox-denylist.md` calls itself *"the primary PII/SEC control"* and ADR-7 carries *"the first whole-inbox scan stays blocked until the denylist review"* as a **live runtime gate** — and no code executes either. The boundary exists as three prose instructions (`/scan-inbox` Step 1 "load the boundary files"; skill A1 "drop any sender whose address/domain/label matches"; B1 "build the query from the allowlist"). A rule that cannot enforce itself is the failure class the rigor layer exists to remove. *Why now:* roadmap v2 Phase 0 — this is the last gate before Phase 1, and YED-81 just shipped the write-side backstop; the read side is the remaining hole. *Press release:* "No thread on the denylist can enter the pipeline, the whole-inbox scan physically cannot run before Alex's review, and every run reports what it skipped."

**2. Goals / Non-goals.** G1 one parser for both boundary files (domains · globs · senders · labels · **status**), reused by `spine_client`'s tier-0 backstop. G2 a `filter` that runs on `search_threads` metadata **before** any aggregation or `get_thread`; Stage A retains metadata only (never snippet/body); Stage B keeps allowlisted-and-not-denylisted only; denylist wins. G3 a `gate` that refuses `discover` while the denylist is DRAFT (ADR-7 D3, mechanized) and refuses `extract` on an uncurated allowlist. G4 skip counts in every run report; a denylisted identity never appears in output. **Non-goals:** no change to what Stage B extracts or how it writes (ADR-9 owns writes); no per-purpose allowlist override for target-company domains (v1 keeps "denylist wins" — revisit only if it drops real signal); no Gmail-side automation; no cron (ADR-7 D4).

**3. Solution + alternatives.** `.claude/scripts/inbox_boundary.py` — section-aware parser (rules/review-log sections contribute no entries; bare words like `docusign` are ignored and reported, never matched), `classify` (sender → domain → label, subdomain suffixes, `*` globs, label-prefix children), `filter --stage A|B`, `gate --stage discover|extract`, `check`, `report`, `--selftest` over a 13-thread fixture inbox + synthetic boundary files in the real format. `/scan-inbox` and the skill call it by name. *Alternatives:* (a) Gmail-query-side exclusion (`-from:bank.example …`) — rejected as the *only* control: query syntax can't express label-children or globs reliably and leaves nothing auditable; kept as an optimization the filter can back. (b) Keep it prose + add a checklist — rejected: that is the current state. (c) Parse the denylist into JSON/YAML — rejected: the markdown file is the human review surface; the parser reads it as-is so the reviewed artifact is the executed artifact.

**4. Leverage & systems.** A #5 rule at the one #6 information flow every inbox thread passes, placed *before* the expensive/risky stage. Guards **Shifting the Burden** (prose standing in for a check) and the **conservative-default** rule from the denylist itself (Stage A drops snippet/body entirely — leakage is not a tuning dial). Direction check: less data retained, not more machinery.

**5. Rabbit holes + pre-mortem.** *Label IDs vs names* — Gmail may return `Label_7`; v1 matches names and the caller maps IDs first (build-time detail, §8). *Glob over-reach* — `*insurance*` could match a legitimate insurtech signal sender; acceptable in v1 by the denylist's own tie-breaker ("when in doubt, exclude"); surfaced in the report counts. *Pre-mortem:* (1) a run "forgets" to call the filter → the gate + filter are the named Step-1/Step-2 mechanism in the command, and the worksheet header must carry the skip counts (a missing count line is a visible defect); (2) the denylist gets edited into a shape the parser misreads → `report` shows what parsed; the review log records changes; (3) the DRAFT gate blocks a legitimate Stage B run → it doesn't: `extract` is allowlist-anchored and passes while DRAFT by design.

**6. Success + eval.** North-star: **boundary-filtered share of threads = 100%** (no thread reaches aggregation or `get_thread` without a `filter` decision); counter-metric: `not-allowlisted` skips in Stage B that Alex later promotes (rising = allowlist too thin, not a filter bug). Registry rows: `{a denylisted sender surfaces in any worksheet/digest → stop the run, fix the parser/filter → in-session}` · `{discover attempted while DRAFT → refused (exit 3) → in-session}`. **Acceptance:** AC1 `--selftest`: Stage A retains zero denylisted rows on the fixture; subdomain, exact sender, label child, glob, spam-section, target-company cases all skip with the right reason class; no denylisted address in output; no snippet retained; Stage B keeps only allowlisted; gate DRAFT→3 / ACCEPTED→0 / missing→2. AC2 the live denylist parses (≥10 domains, ≥5 labels, ≥2 senders) and `report` prints it. AC3 `/scan-inbox` Step 1 calls `gate`, Step 2 pipes metadata through `filter` before any body read; the skill's A1/B1 point at it; run reports carry skip counts. AC4 `spine_client.load_denylist` delegates (one parser; its 21 cases still pass). AC5 **denylist v1 reviewed by Alex → status line `v1 ACCEPTED` + review-log entry** (the human step). AC6 judge ≥ 0.70.

**7. AI-native fields.** Mechanical decisions; Alex owns the lists and the ACCEPTED flip. Failure UX: `gate` prints why it's closed and what flips it. Slope: new sections/labels are data, not code. Living acceptance: `--selftest` + `report`.

**8. Deferred.** Label-ID→name mapping inside the script (needs a `list_labels` snapshot); per-purpose allowlist override for target-company domains; Gmail-query-side pre-exclusion as an optimization; a `Pipeline/boundary-skipped` count label.

**9. Invariants.** ADR-7 D3 (review gate), D5 (no write tools in the distill subagent — untouched), ADR-9 tiers (this is tier 0), no PII in logs (skipped output = reason classes only), `notion-write-gotchas` untouched, git conventions (worktree `esep-yed161`).
